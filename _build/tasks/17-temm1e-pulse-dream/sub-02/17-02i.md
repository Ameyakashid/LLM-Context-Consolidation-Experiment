## 2. Key decisions

### 2.1 `next_fire_time` semantics — approach 2.B (due-aware)

Adopted the research-recommended option: for each enabled entry, emit `now_utc` if `is_checkin_due` already says yes, else the next cron slot. This preserves the legacy `SchedulingHook` behaviour of catching "currently due within staleness window" on the first tick after bot start — approach 2.A would have silently dropped those fires until the next cron edge and broken the sub-03 24-hour parity gate.

Pulse's `_sleep_until_next` (pulse_engine.py:118-121) collapses any `fire_at - now <= 0` into zero sleep, which is precisely how the `now_utc` "fire immediately" signal gets consumed.

### 2.2 Clock injection — `now_provider: Callable`, re-invoked per call

Each of `next_fire_time` and `claim_due_concerns`'s paths calls `self._now_utc()` rather than snapshotting at construction. Tests inject `_frozen_now(moment)`; production gets `datetime.now(timezone.utc)`. This avoids monkeypatching the `pulse_schedule._now_utc` module global (research §3.3, option b).

### 2.3 Cron via `next_fire_after`, not `next_fire_time`

Adapter calls `next_fire_after(schedule, now_utc, tz)` where `now_utc` comes from `now_provider()`. `pulse_schedule.next_fire_time` reads `_now_utc()` internally and would bypass the injected clock. `next_fire_after` has an explicit naive-datetime guard — we piggy-back on it.

### 2.4 Feature flag — majority convention (`== "true"`)

4-of-5 existing `is_*_enabled` helpers use strict `.strip().lower() == "true"`. Disco is the outlier (accepts `"1"`, `"yes"`). Research §1.5 recommended the majority; I pinned it with 17 parametric cases including explicit `"1"` / `"yes"` → `False` assertions (R6).

### 2.5 Staleness guard reuse — not duplicated

`claim_due_concerns` calls `is_checkin_due(entry, current_date, current_time)` directly. No re-implementation, no "wrapper layer" — satisfies description §Risks ("DO NOT duplicate the staleness-guard logic") and code-rules §16 ("Check if logic exists before writing new code").

### 2.6 `advance_last_run` as named seam

Description §5 mandates the export. It's a one-line wrapper over `store.record_fired`, which technically brushes AI-Anti-Slop rule §3 ("No unnecessary abstractions"). Kept anyway because (a) the spec explicitly requires the symbol, (b) sub-03 needs a clear call site to mock in tests, and (c) the research agent concurred (§3.7).

### 2.7 Naive-datetime rejection at adapter boundary

Both `claim_due_concerns(now)` and the internal `_now_utc()` raise `ValueError` on naive input, mirroring `pulse_schedule.next_fire_after`'s guard style (pulse_schedule.py:135-139). Pulse hands UTC so in production this never fires; tests verify the guard is live (R3).

### 2.8 Retroactive fires ≤ `now_utc` (R1 mitigation)

When an entry is already due, the adapter emits *exactly* `now_utc` as the candidate — not a sentinel past-time. Pulse computes `until = fire_at - now`; using `now_utc` guarantees `until == 0` and immediate consumption on the same tick.

### 2.9 `target_time` minute-resolution truncation

`time(H, M, S)` maps to cron `"M H * * *"`, which silently rounds seconds to zero. Documented in the module docstring as an adapter invariant; defaults only use `time(H, 0)` so no live config hits this (R7).

### 2.10 `tzdata` Windows marker rather than unconditional pin

`tzdata>=2024.1; sys_platform == "win32"` keeps the macOS dep-set minimal (Mac ships IANA natively). Addresses R2 without bloating the Mac install.

## 5. Notes for sub-03

1. **Wiring point.** Construct `PulseCheckinStore(checkin_store, get_user_timezone())` from `hook_factory.py` when `is_pulse_engine_enabled(os.environ)` is True. The legacy `SchedulingHook` stays in place under flag-off.
2. **Dispatch flow.** After draining a `PulseEvent` from the queue: `checkin_type = concern_id_to_checkin_type(event.concern_id)` (None-guard for safety even though types are fixed); render the check-in via the existing `evaluate_checkin` / `format_checkin_block` path; finally `advance_last_run(store, checkin_type, today)` where `today` comes from `datetime.now(tz).date()`.
3. **Schedule-change notification.** When the user changes `target_time` or toggles `is_enabled` via tools, call `pulse.schedule_notifier().set()` so Pulse recomputes `next_fire_time` instead of sleeping on the stale value.
4. **Open issue from sub-01 #1 (still open).** `Pulse._query_next_fire_time` only swallows `asyncio.TimeoutError`; any other exception from `next_fire_time` still kills the loop. Our adapter does not raise under well-formed input (R10) — defensive, but sub-03 should still be aware of the narrow guard.
5. **`tzdata` dep.** Fresh Windows clones now resolve IANA zones without relying on transitive installs. No action needed in sub-03; just a quieter CI matrix.
