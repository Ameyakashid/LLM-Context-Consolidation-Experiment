## 2. Key decisions and why

### 2.1 Pydantic discriminated union for `Schedule`

Chosen over frozen-dataclass (research §3a option B) and plain `typing.Union` (option C). The repo's existing data-model taste is consistently Pydantic (`checkin_schedule.CheckInEntry`, buffer entries, calendar types); matching that idiom keeps the new module consistent with the project. `TypeAdapter(Schedule)` gives free JSON/python round-trip for the discriminated union without hand-written serialisers — every test in §4 of the research plan ran with less glue code than the dataclass equivalent would have required.

### 2.2 JSON tagging: `kind` discriminator (deliberate divergence from Rust serde)

Rust serde's externally-tagged default is `{"At": "..."}`. Pydantic's idiomatic form is internally-tagged `{"kind": "at", "at_utc": "..."}`. Because there is no Rust↔Python wire round-trip here — only Python-side persistence — the Pydantic idiom wins. Recorded in the `pulse_schedule.py` module docstring. If sub-02 or sub-03 ever needs Rust compatibility, we swap the discriminator for a Pydantic custom validator without a model-shape change.

### 2.3 `cron5_to_cron7` omitted (research §3b)

Rust's 7-field helper exists because the `cron` crate requires it; `croniter` accepts 5-field expressions natively. The Python port skips the helper entirely and documents the omission in `ScheduleCron`'s docstring and the module docstring. The Rust-source `cron5_to_cron7_conversion` test is replaced with `test_cron_expression_parses_via_croniter`, which asserts the 5-field form survives through `next_fire_time`.

### 2.4 `tokio::select!` → `asyncio.wait(FIRST_COMPLETED)` with explicit loser cancellation

Follows research §3c option A. Every loop iteration creates three named tasks, races them, and cancels the two losers with `_cancel_pending` (the `try/except CancelledError` pattern). Matches `tokio::select!`'s cancel-losing-branches semantics (R4). Helper functions kept private and tiny (< 10 lines each) per code-rules.md:66 (no single-purpose util files — they live in the same file).

### 2.5 `asyncio.Event` for `Notify` with `.clear()` after wake

Chosen over `asyncio.Condition` (research §3c). When `notify_task` is the winner, the loop calls `self._schedule_changed.clear()` before `continue`, preventing the busy-spin risk flagged as R5. Sequential `.set()` calls while the loop is mid-iteration collapse into a single wake — same behaviour as `tokio::sync::Notify`.

### 2.6 Pydantic validation for invalid cron expressions intentionally deferred

Rust's `Schedule::Cron(String)` holds an unvalidated string; parsing happens in `next_fire_time`, which swallows the error via `.ok()?`. The port mirrors this: `ScheduleCron` accepts any string at construction, and `_cron_next_strictly_after` catches `CroniterBadCronError` / `ValueError` and returns `None`. No validator. This matches `test_next_fire_time_cron_invalid_returns_none` and `test_next_fire_after_cron_invalid_returns_none`.

### 2.7 `PulseStoreProtocol` lives inside `pulse_engine.py`

Research §3d preferred. `Protocol` (not `@runtime_checkable`) is enough — mypy enforces structurally, and `FakePulseStore` in the tests carries no explicit inheritance. No separate file; only two methods, used in one place.

### 2.8 `_query_next_fire_time` split from `_sleep_until_next`

The Rust source inlines the `tokio::time::timeout` inside `sleep_until_next`. I split out the timeout-handling into a private `_query_next_fire_time` method so the control flow (`fire_at is None` → idle poll; otherwise compute delta and sleep) is linear in `_sleep_until_next`. No functional change; easier reading. Documented via structure, not a comment.

### 2.9 Claim-due-concerns error swallow uses generic `Exception`

Research R10. The concrete store adapter (sub-02) will raise domain-specific errors; until that type exists, catching `Exception` is the faithful port of Rust's `Err(e) => log + return`. The comment in `pulse_engine.py:140` cites the Rust line it mirrors.

### 2.10 Channel-closed detection is NOT ported

Rust's `mpsc::send().is_err()` detects a dropped receiver. Python's `asyncio.Queue` has no receiver-drop concept (shutdown appeared in 3.13; the project runs 3.12). The loop in `_fire_due_concerns` simply `await`s `queue.put`; if no consumer exists, `put` blocks once the queue fills (64 items). This is a behavioural deviation, not a functional gap — sub-03's consumer will always drain. Documented here as an explicit deviation and is the only such case.

## 4. Deviations from source (full list)

| # | Where | Deviation | Why |
|---|---|---|---|
| D1 | `pulse_schedule.py` Schedule JSON shape | Internally-tagged `{"kind": ..., ...}` instead of Rust serde externally-tagged `{"Variant": ...}` | No wire compatibility requirement; Pydantic idiom. (See §2.2.) |
| D2 | `pulse_schedule.py` cron parsing | No `cron5_to_cron7` helper | `croniter` accepts 5-field natively. (See §2.3.) |
| D3 | `pulse_engine.py` `_query_next_fire_time` | Private method extracted from `_sleep_until_next` | Readability; no behavioural change. (See §2.8.) |
| D4 | `pulse_engine.py` `_fire_due_concerns` channel close | No `is_err()` / `break` on receiver-drop | `asyncio.Queue` < 3.13 lacks shutdown signal. (See §2.10.) |
| D5 | `pulse_engine.py` error catch in `_fire_due_concerns` | `except Exception` instead of `Err(Temm1eError)` | Faithful to Rust's log-and-return swallow; narrow type comes from sub-02. (See §2.9.) |
| D6 | `pulse_engine.py` `Pulse.create` classmethod | Rust's tuple-returning constructor replaced with `create()` classmethod + plain `__init__` | Keeps `__init__` type-friendly for mypy while preserving the `(pulse, rx)` return contract. |
| D7 | `pulse_schedule.py` `next_fire_after` naive-datetime guard | Raises `ValueError` on naive `after` | Rust's `DateTime<Utc>` is type-constrained; Python's `datetime` isn't, and silently mis-interpreting a naive datetime as UTC would cause DST bugs. Cheap explicit guard at the boundary. |

Everything else — names, numeric constants (64/10/60), semantics, test intent — is 1:1.

## 6. Notes for sub-02 and sub-03

- The `PulseStoreProtocol` is the sole contract surface; sub-02's adapter conforms structurally without inheriting.
- `pulse_engine.CHANNEL_MAX_SIZE`, `STORE_QUERY_TIMEOUT_S`, `IDLE_POLL_SECONDS` are module-level module-level constants; sub-02/03 may `monkeypatch` them in tests (as `test_pulse_engine.py` already does), but production wiring should not mutate them.
- `Pulse.create(store, cancel)` is the ergonomic constructor; sub-03 should call it exactly once when wiring the engine into `gateway_runner.py` and feed the returned queue into the event consumer.
- `PulseEvent` is a Pydantic model (not an enum) — future variants get sibling classes with distinct `kind` literals and a discriminated union alias, mirroring `Schedule`.
