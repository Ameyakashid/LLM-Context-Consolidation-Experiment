## Issues Found

### MEDIUM — store-side exception swallow is incomplete (pulse_engine.py:123-135)

The Rust source in `pulse.rs:70-73` explicitly swallows **both** timeout and store-side `Result::Err` via the double `.unwrap_or`:

```rust
let next = tokio::time::timeout(Duration::from_secs(10), self.store.next_fire_time())
    .await
    .unwrap_or(Ok(None))   // timeout → None
    .unwrap_or(None);      // store Err → None
```

The Python port only catches `asyncio.TimeoutError`:

```python
try:
    return await asyncio.wait_for(self._store.next_fire_time(), timeout=STORE_QUERY_TIMEOUT_S)
except asyncio.TimeoutError:
    ...
    return None
```

If the future sub-02 store adapter raises any non-timeout exception from `next_fire_time()` (e.g. an `sqlite3.OperationalError` during a brief DB contention), the exception propagates through `_sleep_until_next`, into the `done` set of `asyncio.wait`, and `_reraise_task_errors` (pulse_engine.py:167) re-raises it out of `Pulse.run`. The loop dies. Rust's equivalent logs-and-continues on the same failure mode.

**Impact:** Rare in practice, but divergent from the "preserve semantics" mandate in the spec. Not caught by tests — `RaisingStore` only raises in `claim_due_concerns`, mirroring the already-handled path.

**Not recorded in impl §4 "Deviations from source".** Should be either (a) fixed by widening the `except` to `(asyncio.TimeoutError, Exception)` with the same logged-swallow as `_fire_due_concerns`, or (b) called out explicitly as deviation D8 with a WHY line.

**Suggested fix:**

```python
async def _query_next_fire_time(self) -> datetime | None:
    try:
        return await asyncio.wait_for(
            self._store.next_fire_time(),
            timeout=STORE_QUERY_TIMEOUT_S,
        )
    except asyncio.TimeoutError:
        logger.warning(...)
        return None
    except Exception as exc:
        # Mirrors Rust pulse.rs:73 `.unwrap_or(None)` on store Err.
        logger.error("Pulse store.next_fire_time() failed: %s; treating as no-schedule", exc)
        return None
```

### MEDIUM — `ScheduleAt.at_utc` accepts naive datetimes silently (pulse_schedule.py:40-46, 113-114)

`ScheduleAt` is a Pydantic model with `at_utc: datetime`; Pydantic accepts both naive and tz-aware datetimes by default. `next_fire_time` then does `schedule.at_utc > now` where `now = datetime.now(timezone.utc)` is tz-aware — this comparison raises `TypeError: can't compare offset-naive and offset-aware datetimes` at call time, deep inside `next_fire_time`, with no context about the misconfiguration.

`next_fire_after` has a symmetric guard (line 135-139) that rejects naive `after` with a clear `ValueError`. The asymmetry is inconsistent.

**Impact:** A misconstructed schedule (e.g. from a config file deserialized without a timezone) crashes `next_fire_time` with a cryptic stdlib TypeError instead of the caller hitting a validation error at construction. Low probability given current call sites, but becomes surface area for sub-02 when schedules start flowing in from persisted JSON.

**Suggested fix:** Add a Pydantic field validator on `ScheduleAt.at_utc` that rejects naive datetimes with a clear message, mirroring the `next_fire_after` guard. Five lines.

### LOW — `ScheduleEvery.every_seconds > 0` tightens Rust's contract (pulse_schedule.py:55)

Rust's `Duration::from_secs(0)` is legal; the Python port uses `Field(gt=0)` which rejects zero. Not documented as a deviation. Acceptable (zero-second repeat would busy-loop) but inconsistent with the stated "1:1 port" and undocumented.

**Suggested fix:** Either document as D8, or relax to `ge=0` to match Rust.

### LOW — `_cron_next_strictly_after` catches only `(CroniterBadCronError, ValueError)` (pulse_schedule.py:92)

croniter can raise other exception types in some edge cases (e.g. `CroniterNotAlphaError`, `KeyError` on malformed hash-expressions). Current test coverage (`"not a cron"`) exercises only the common path. If a future schedule carries an unusual malformed string, the exception escapes `_cron_next_strictly_after` rather than returning `None`.

**Suggested fix:** Broaden to `except Exception` with a logger.warning, or enumerate the croniter exception family explicitly.
