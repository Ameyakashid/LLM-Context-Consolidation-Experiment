## Goal recap

Build the Dream State engine: a side-effect-isolated orchestrator that
gathers recent memories + tasks + session log excerpts, hands them to
an injected `llm_caller`, parses the response under a strict
5-category schema (`commitment` / `deadline` / `blocker` /
`energy_state` / `context_switch`), and writes the validated insights
back into `MemoryEntryStore`. Pure helpers are separated from the
stateful engine. The engine is **inert** in this subtask — sub-05
instantiates it inside the Pulse tick loop behind `DREAM_STATE_ENABLED`.

## Design decisions

### Split into three modules to honor the 300-line cap

Research plan §3.10 budgeted ~270 lines for a single `dream_engine.py`.
That estimate underweighted docstring + blank-line overhead. A
monolithic file landed at 474 lines. Rather than squeezing the code,
three modules were produced that map onto code-rules §Structure:

- `dream_types.py` — types + constants (no logic)
- `dream_helpers.py` — pure functions (no state)
- `dream_engine.py` — the stateful orchestrator

Each file re-exports the cross-cutting symbols under `__all__` so
importers can keep the flat `from dream_engine import DreamEngine,
DreamState, ...` surface the description.md expected.

### `<<TOKEN>>` substitution instead of `str.format`

The DREAM.md prompt embeds a JSON schema with literal `{...}`. Running
it through `str.format` would trip on every brace. The template uses
`<<RECENT_MEMORIES>>` / `<<SESSION_EXCERPTS>>` / etc., and
`build_consolidation_prompt` applies plain `str.replace` in a known
order. Five placeholders, one final `[:MAX_PROMPT_CHARS]` truncation.

### Dedup key: `(category, content)` over active entries only

`_apply` computes a `set[(category, content)]` from
`list_active_entries()` before the write loop and updates it as each
insight lands. This makes two consecutive `_apply` calls on the same
output insert each insight exactly once — the property the
`TestApplyIdempotent.test_duplicate_insight_not_rewritten` test pins
down. Resolved/retired entries are excluded from the dedup set so the
Dream can legitimately re-surface an insight after it was resolved.

### Dream-generated entries excluded from their own input window

`_is_dream_generated(entry)` checks `metadata["source"] == "dream_state"`
and filters the gather step. Without this, the next run would see its
own prior insights as "recent memories" and hallucinate reinforcement
loops. The resolved bucket still admits them (so Dream can still see
what it resolved in the last cycle).

### Four spec-named pure helpers kept under 30 lines each

Research plan pinned four function names:

- `gather_consolidation_context` — 24 lines
- `build_consolidation_prompt` — 20 lines
- `parse_consolidation_response` — 18 lines
- `sanitise_excerpt` — 7 lines

Enforcement required extracting `_bucket_entries`, `_decode_response`,
`_validate_insight`, `_validate_resolves`, `_parse_session_line`,
`_read_session_excerpts`, `_cap_excerpts`, `_format_entry_lines`,
`_stringify`, `_is_dream_generated`. Private helpers carry no `__all__`
entry; import surface is exactly the four spec names + the cost
estimator + the dataclasses re-exported from `dream_engine`.

### Engine stays inert until sub-05 wires it

The module is fully constructible, fully testable, and fully verifiable
in isolation, but nothing in `run_gateway`, `custom_gateway`,
`gateway_runner`, or `pulse_engine` imports it today. The `run`
coroutine signature matches what sub-05's Pulse dispatcher will call.
The `reset_state` method exists specifically so sub-05 can drive a
single long-lived engine across many ticks rather than re-constructing
per tick (leaves that choice open).

### Oversize-content policy: reject + record in `dropped`

Research §4 pinned "reject+skip" over "truncate-then-keep". The insight
is excluded from `insights`; `(snippet, "oversize_content")` lands in
`dropped`. Operator can grep logs (`log.warning`) or inspect
`DreamRunResult` if they want the trail. Same pattern for unknown
categories, empty content, non-dict insights, non-string resolve ids,
and phantom ids.

### Cost envelope — Grok pinned at $0.0037/run (well under $0.01)

`estimate_per_run_cost_usd(MAX_PROMPT_CHARS=6000,
MAX_COMPLETION_TOKENS=800, "x-ai/grok-4.1-fast")` returns
`(6000/4) * 0.20/1_000_000 + 800 * 0.50/1_000_000 = $0.0007`. The
0.01 cap in `DreamEngine.estimated_cost_per_run_usd` is 14× headroom,
which matches the research spec.

## Deviations from research plan

1. **Module split 1 → 3.** Research §3.10 assumed a single file.
   Explained above. Import surface preserved via re-export.
2. **No `StrEnum`.** Research §7 suggested `enum.StrEnum`. The venv is
   Python 3.10; `StrEnum` is 3.11+. `class DreamState(str, Enum)`
   gives the same string-value behaviour with no call-site change.
3. **`<<TOKEN>>` instead of `{token}`.** Research §5 implied
   `str.format`. Switched because the prompt's JSON schema contains
   literal braces. Behavior is identical; surface syntax differs.
4. **Gitignore negation.** Research did not anticipate the
   agent-framework `templates/` exclusion swallowing the app's
   `workspace/templates/`. Added `!workspace/templates/`; verified
   the agent-framework `templates/` root-level exclusion still bites.

## Handoff to sub-05

Sub-05 should:

1. Construct a long-lived `DreamEngine` at gateway startup with
   `memory_store=bot.memory_store`, `task_store=bot.task_store`,
   `session_log_path=nanobot_home/sessions/current.jsonl`,
   `llm_caller=bot.openrouter_client.complete_json`,
   `clock=lambda: datetime.now(timezone.utc)`,
   `prompt_template=(workspace_root / "templates" / "DREAM.md").read_text(...)`.
2. Call `await engine.run()` on each Pulse tick where the state
   machine enters the Dream window (quiet hours); call
   `engine.reset_state()` before each subsequent run.
3. Gate the whole thing behind `DREAM_STATE_ENABLED`.
4. Log the returned `DreamRunResult` for operator visibility.

No changes to the `DreamEngine` surface are required — all injection
points are already in place.
