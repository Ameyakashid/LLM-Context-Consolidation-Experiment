## Goal recap

Wire the sub-01 Pulse engine + sub-02 `PulseCheckinStore` adapter into the
live ADHD gateway behind the `PULSE_ENGINE_ENABLED` flag. When the flag
is OFF, the heartbeat → `SchedulingHook.get_due` → `record_fired` path
runs unchanged. When the flag is ON, Pulse drives claim timing, a
dispatcher evaluates cognitive state and pushes formatted blocks onto a
shared queue, and the hook injects one pre-rendered block per tick.

The 24-hour parity gate (AC#2) is the primary correctness bar: both
paths must emit the same set of `(checkin_type, fire_date)` pairs and
byte-identical prompt blocks under the baseline state.

## Design decisions

### Path C (pending-queue drain) chosen over Path A / Path B

Research report enumerated three injection surfaces:

* **Path A** — dispatcher calls `agent.process_direct` directly.
  Rejected: spawns a new session turn at fire time, diverges from the
  legacy turn shape (single system-prompt mutation inside the live
  heartbeat iteration), and forces duplication of
  `_pick_heartbeat_target` out of `gateway_runner`.
* **Path B** — dispatcher posts to `bus.publish_inbound`. Rejected:
  nanobot's inbound queue expects user/assistant messages, not
  system-prompt suffixes.
* **Path C** — dispatcher pushes onto a `PendingCheckinQueue`;
  `SchedulingHook` drains it inside the existing heartbeat iteration.
  **Chosen** because it preserves the exact legacy turn shape and makes
  the 24-hour parity gate (AC#2) byte-identical: same
  `format_checkin_prompt` call in both paths, same `messages[0]` write
  site, same hook ordering downstream.

### Shared state-accessor derivation from the hook chain

`PulseCheckinDispatcher` must see the same `StateName` that
`StateResponseHook` wrote. Rather than re-plumbing the state closure
through the gateway, `_derive_state_accessor` walks the built hook list
after `create_hooks` returns and binds a closure against the first
`HookAdapter` whose `.wrapped` is a `StateResponseHook`. Fails fast with
a construction error if the chain is malformed.

### Dedup key on the pending queue

`PendingCheckinQueue.push` returns `False` when
`(checkin_type, fire_date)` is already seen. Motivation: if the Pulse
consumer crashes after claim but before dispatch, restart re-claims
from `claim_due_concerns` and could re-emit the same concern.
Idempotency at the queue boundary quarantines that failure mode.

### Bundle lifecycle owned by `PulseBundle`

`PulseBundle` owns the two `asyncio.Task`s (`pulse-engine`,
`pulse-consumer`) and their cancel `Event`. `start()` is single-use (a
second call raises). `stop()` sets cancel, then drains each task with
`asyncio.wait_for(timeout=PULSE_SHUTDOWN_TIMEOUT_S=5.0)`; on timeout it
force-cancels and swallows `CancelledError`. Ordering in
`gateway_runner.run.finally` is deliberate: `await pulse_bundle.stop()`
runs **before** `heartbeat.stop()` and `cron.stop()` so the dispatcher
can still touch the schedule store during its last drain without
racing a half-torn-down environment.

### `_setup_cron_callback` extraction

`gateway_runner.py` was at 308 lines before sub-03 added the pulse
lifecycle (~13 lines). To fit under the 300-line cap, the 57-line
`_setup_cron_callback` closure was lifted verbatim into
`cron_callback_setup.py`. Body unchanged; call site renamed to
`setup_cron_callback`. This is an incidental cleanup noted as a
deliberate deviation from the research plan, driven solely by the line
cap.

  a `TaskStoreProtocol` for flexibility. The gateway always injects a
