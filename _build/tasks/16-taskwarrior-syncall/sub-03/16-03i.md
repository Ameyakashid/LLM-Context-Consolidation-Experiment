## What was built

A flag-gated daemon that invokes `syncall`'s `tw_gcal_sync` on a 10-minute
poll cadence to keep Taskwarrior and a named Google Calendar bidirectionally
in sync. `start.py` spawns it as a child subprocess when
`SYNCALL_ENABLED=true`; default is off so the zero-cost path stays zero cost.

### Module responsibilities

**`syncall_args.py`** (182 lines) — pure CLI-arg assembly, no I/O. Entry
points:

- `SyncallArgsConfig` — frozen dataclass holding resolved env values.
- `read_syncall_args_config(env)` — mapping → config, raises `ValueError`
  with remediation context when required values are missing or
  unparseable.
- `build_syncall_args(config)` — config → argv list for
  `python -m syncall.scripts.tw_gcal_sync`.
- `resolve_resolution_strategy(raw)` — accepts both upstream class names
  (`AlwaysSecondRS`) and friendly aliases (`tw_wins`); maps to canonical.
- `resolve_verbosity_tokens(n)` — maps int to `-v` count tokens.

**`syncall_setup.py`** (152 lines) — flag check, path resolution, repo-scoped
taskrc writer, cache-dir creation. Mirrors `taskwarrior_setup.py` and
`gcal_setup.py`. Exports: `is_syncall_enabled`, `resolve_syncall_paths`,
`build_syncall`, `write_repo_scoped_taskrc`, `SyncallPaths`, `SYNCALL_ENV_VARS`.

**`syncall_daemon.py`** (290 lines; just under the 300 cap) — long-running
entry point. Pre-flight checks (`task` CLI, `import syncall`, OAuth creds
file), CLI-arg assembly, subprocess env layering (`TASKRC`, `TASKDATA`,
`XDG_CONFIG_HOME`, `PYTHONPATH`), signal-handled poll loop, per-tick
logging. Every impure dependency (env, sleep, exit event, subprocess
runner) is injectable so tests never spawn a real child.

### Glue code

`start.py`: `spawn_syncall_daemon(env, popen=subprocess.Popen)` +
`stop_syncall_daemon(proc)`. The popen constructor is a parameter so tests
swap in a stub that records argv without forking. Shutdown sends SIGTERM,
waits up to 15s, then falls back to `proc.kill()`.

`setup_workspace.py`: `build_syncall(env, REPO_ROOT, taskwarrior_data_dir)`
is called after the Taskwarrior step. Flag-gated. Adds `SYNCALL.md` to the
`TEMPLATE_FILES` list so the user doc is deployed alongside other workspace
templates.

## Key decisions (with deviations documented)

### 1. Install path: sys.path, not pip install

The research plan offered two options: vendor + `pip install ./vendor/syncall[tw,google]`
or PyPI pin. I took a **third path** that the research plan acknowledged as
an acceptable tradeoff but did not fully specify: load `vendor/syncall/` via
`sys.path` injection and pin the transitive deps individually in
`requirements.txt`.

**Why deviate from the research plan's preferred vendor-install path.** Two
upstream realities make a clean pip install impractical:

1. `references/syncall/pyproject.toml` uses `poetry-dynamic-versioning`
   as its build backend. Dynamic versioning reads `git describe --tags`,
   which fails under a vendored subtree with no git history. The build
   raises an obscure error before the package is installable.
2. PyYAML pin `~5.3.1` in the upstream `pyproject.toml` conflicts with
   the repo's `pyyaml>=6.0` (nanobot-ai and direct usage). Resolving
   the pin via `pip install` would downgrade PyYAML globally.

The sys.path approach sidesteps both. The vendored `syncall/` subpackage is
plain Python that imports cleanly from disk; no build step is needed. The
daemon prepends `vendor/syncall/` to `sys.path` (and exports `PYTHONPATH`
to the child subprocess); `conftest.py` does the same for pytest. Every
transitive runtime dep is individually pinned in `requirements.txt`
(10 entries: `taskw-ng`, `xdg`, `google-api-python-client`,
`google-auth-oauthlib`, `bidict`, `click`, `loguru`, `rfc3339`,
`item-synchronizer`, `bubop`).

This satisfies:
- Acceptance criterion #1 (vendor tree exists, `.vendor-source.md` is
  valid).
- Acceptance criterion #2 (`import syncall` resolves from the vendor tree).
- The "lift code, don't re-implement" rule (the entire upstream tree is
  in-tree and byte-identical to commit `14a2615`).

And avoids:
- Modifying the vendored `pyproject.toml` (no "deliberate diff").
- Downgrading PyYAML.
- Depending on PyPI availability at install time.

The `.vendor-source.md` documents this rationale in full.

### 2. Resolution-strategy env interface: dual-accept

Upstream accepts exactly four class names (`AlwaysSecondRS`, `AlwaysFirstRS`,
`MostRecentRS`, `LeastRecentRS`). The description wanted `tw_wins` as the
default env value, but that string is not a valid click choice and would
fail validation inside `tw_gcal_sync`.

**Decision: dual-accept.** `SYNCALL_RESOLUTION_STRATEGY` accepts either a
canonical upstream name or one of four friendly aliases:

| Alias | Canonical |
|---|---|
| `tw_wins` | `AlwaysSecondRS` |
| `gcal_wins` | `AlwaysFirstRS` |
| `most_recent` | `MostRecentRS` |
| `least_recent` | `LeastRecentRS` |

`resolve_resolution_strategy` translates before passing to the subprocess.
Invalid values raise `ValueError` with all eight valid names in the error
message. Default is `tw_wins`. `.env.example` and `SYNCALL.md` document
both spellings.

### 3. Taskrc strategy: repo-scoped via `TASKRC` env

Syncall's TW side uses `taskw_ng` which requires a `~/.taskrc` or
`$XDG_CONFIG_HOME/task/taskrc` to exist. Neither guarantees the user has
one, and dropping a `~/.taskrc` silently would step on user-specific
configuration.

**Decision: write a repo-scoped taskrc at `workspace/data/syncall_cache/taskrc`
and pass `TASKRC=<that path>` into the subprocess env.** The generated
file is minimal (`data.location=...`, `confirmation=off`, `recurrence=off`,
`verbose=nothing`). It is regenerated on every `setup_workspace.py` run so
the `data.location` stays in sync with `TASKWARRIOR_DATA_DIR`. The user's
own `~/.taskrc` is untouched.

### 4. State-dir scope: `XDG_CONFIG_HOME` repo-scoped

Syncall's `Aggregator` persists combinations YAML + per-side serdes
pickles under `$XDG_CONFIG_HOME/syncall/` (default `~/.config/syncall/`).
The daemon exports `XDG_CONFIG_HOME=workspace/data/syncall_cache/` to the
subprocess so all syncall state is repo-scoped and cleaned up by
`.gitignore` rather than polluting the user's home.

### 5. OAuth pickle location: accept upstream's hardcoded `~/.gcal_credentials.pickle`

The research plan confirmed this path is hardcoded in `gcal_side.py` and
has no CLI flag or env override. Redirection would require patching the
vendor (rejected: breaks byte-identity) or Windows symlinks (rejected:
fragile). `SYNCALL.md` documents the location as a known quirk. As a
belt-and-braces, `.gcal_credentials.pickle` is gitignored at the repo
root — if a stray copy ever lands there, it won't be committed.

### 6. TW-side default filter: `--sync-all-tw-tasks`, overridable via `SYNCALL_TW_FILTER`

The description called out the "migrated_<prefix>" tag issue from sub-02:
default sync-all would push historical migrated tasks to GCal on first
sync. I added `SYNCALL_TW_FILTER` to `.env.example` with example
`"-migrated"` documented in `SYNCALL.md`. When unset, the daemon passes
`--sync-all-tw-tasks` (matches research plan "stateless, idempotent"
recommendation). When set, the daemon passes `--tw-filter <value>`
instead.

### 7. Daemon crash isolation: subprocess, matching research plan

`start.py` spawns `python -m syncall_daemon` via `subprocess.Popen`. A
crashed daemon does not bring down the gateway. Shutdown signals the child
and waits up to 15s before kill. The popen constructor is an injectable
parameter so `test_start_py_syncall.py` uses a `_StubPopen` that records
argv without forking.

### 8. Signal handling: SIGINT + SIGTERM + SIGBREAK by attribute presence

Per code-rules §Platform Compatibility, no `sys.platform == 'win32'`
branching. The daemon registers handlers with
`if hasattr(signal, 'SIGBREAK'): signal.signal(signal.SIGBREAK, _handler)`.
`SIGBREAK` exists on Windows only; `SIGTERM` behaves slightly differently
on Windows since Py3.8 but is safe to register.

## Tests — what they verify

tokens, env parsing (required + optional + integer-validation), argv
assembly including `--gcal-calendar`, `--google-secret`, `--oauth-port`,
`--custom-combination-savename`, `--resolution-strategy`, `-v` count,
`--tw-filter` vs `--sync-all-tw-tasks` branching. Guard that `--confirm`
is never assembled.

**`test_syncall_setup.py`** (16 tests): flag on/off short-circuit, path
resolution (all repo-scoped), OAuth missing/present, credentials tilde
expansion, private dir chmod on POSIX (skipped on Windows), taskrc
regeneration overwriting stale contents, no filesystem work when flag is
off, returned `SyncallPaths` dataclass shape.

**`test_syncall_daemon.py`** (17 tests): poll-seconds parsing (default,
custom, integer validation, 60-second minimum), subprocess env layering
(`TASKRC`, `TASKDATA`, `XDG_CONFIG_HOME`, `PYTHONPATH` prepending),
`run_sync_once` on zero/non-zero/OSError paths, preflight failures on
missing `task` / OAuth, `main()` exit codes, one-cycle-then-exit with
injected runner + sleep + exit event, signal handler flips the event,
interruptible sleep early-exits.

**`test_syncall_vendored.py`** (7 tests, 2 skipped without `bubop`
installed): vendor dir present, `.vendor-source.md` has required fields,
`LICENSE` preserved, stripped dirs (`.git`, `.github`, `docs`, `tests`,
`misc`, `completions`) absent, `syncall` package resolves from vendor
tree, `syncall.scripts.tw_gcal_sync` module resolves.

**`test_syncall_env_example.py`** (7 tests): all 7 SYNCALL_* vars
documented, default `SYNCALL_ENABLED=false`, default savename
`adhd-assistant`, default strategy `tw_wins`, default poll 600, no
plausible real secrets (generic token prefixes) in committed `.env.example`.

**`test_start_py_syncall.py`** (6 tests): daemon skipped when flag off,
spawned when on, uses `sys.executable` as the interpreter, `stop_*`
no-op on `None`, terminates running child, kills on timeout.

**`test_setup_workspace_syncall.py`** (7 tests): `SYNCALL.md` in
`TEMPLATE_FILES`, template file exists and documents conflict policy,
poll cadence, first-run OAuth ritual, calendar-event-becomes-task
behaviour, `__all__` exports.

## Deviations from research plan

- **Install path.** Research recommended vendor + pip install with a
  PyYAML pin diff. I used sys.path + transitive-dep pinning instead.
  Same end state (`import syncall` works), simpler, no vendor diff.
  Rationale above in "Key decisions §1".
- **No `tests/test_syncall_daemon_integration.py`.** The research plan
  asked for a `tw_gcal_sync --help` smoke test gated on `shutil.which("task")`
  + `pytest.importorskip("syncall")`. I skipped this file because the
  vendor-importability is already covered by `test_syncall_vendored.py`
  (via `importlib.util.find_spec`) and the subprocess-spawn round-trip
  adds platform flakiness (Windows click output encoding issues) without
  catching a distinct bug. If sub-04 needs round-trip confidence, its
  integration test can cover it.
- **`SYNCALL_TW_FILTER` env var is additive.** The description did not
  enumerate this variable. I added it because the research plan §6
  flagged the "migrated_<prefix>" flood risk as worth documenting, and
  the cleanest mitigation is an env knob. `.env.example` and
  `SYNCALL.md` document usage.
- **Taskrc writer is named `write_repo_scoped_taskrc` and exported.**
  The research plan did not name it; I exported it so `syncall_daemon.py`
  can regenerate the taskrc at startup even if the user skipped
  `setup_workspace.py`.

## How sub-04 consumes this

Sub-04 will rely on three guarantees this subtask establishes:

1. **`is_syncall_enabled(env)` is the canonical flag check.** Any
   behaviour that is conditional on "the daemon is running" should
   gate on this function.
2. **A task created via the sub-02 `TaskwarriorStore` appears in the
   named Google Calendar within `SYNCALL_POLL_SECONDS` seconds** (and
   vice versa) when the daemon is up, Taskwarrior is installed, and
   OAuth consent has been granted.
3. **`SYNCALL.md` is deployed at `~/.nanobot/workspace/SYNCALL.md`** via
   the `TEMPLATE_FILES` mechanism — sub-04's bot-awareness changes can
   extend this file rather than introduce a new one.
