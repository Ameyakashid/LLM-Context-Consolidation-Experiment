## What was built

### 1. Vendored MagicMirror² tree

`references/MagicMirror/` → `magicmirror/` with `.git/`, `.github/`, `.claude/`,
`node_modules/` stripped. Each of the three modules followed the same
pattern into `magicmirror/modules/<name>/`. sha256 on every vendored
`package.json` matches upstream (asserted by `TestVendorByteIdentity`).

**Windows quirk fix:** `shutil.rmtree(.git/)` failed with `PermissionError
[WinError 5]` on packed `.idx` files that git marks readonly. Resolved
by wrapping the removal in a Python helper that chmods `S_IWRITE` and
retries — no platform fork leaked into the production code, this was
one-shot tooling during vendoring.

**Pin files (`.vendor-source.md`):** upstream repo URL, commit SHA,
semver, vendoring date, stripped-dirs list. Core `.vendor-source.md`
additionally documents why `npm install` for the MM root must pass
`--ignore-scripts`: MagicMirror's `postinstall` runs `git clean -df`
which would nuke our vendored `config/config.js.template` and any other
non-upstream files we legitimately keep in the tree.

### 2. `magicmirror_setup.py` — single control point

Seven exports (three public functions + three constants):

```python
MAGICMIRROR_WEBHOOK_TEMPLATE_NAMES: tuple[str, str, str] = (
    "state_change", "buffer_alert", "missed_checkin",
)
MODULE_NAMES: tuple[str, str, str] = (
    "MMM-WebHookAlerts", "MMM-Markdown", "MMM-pages",
)
MAGICMIRROR_CONFIG_VARS: dict[str, str] = {
    "MAGICMIRROR_HOST": "0.0.0.0",
    "MAGICMIRROR_PORT": "8080",
    "MAGICMIRROR_IP_WHITELIST_JSON": '["127.0.0.1", "::1", ...]',
}

def is_magicmirror_enabled(env: Mapping[str, str]) -> bool
def detect_node_npm() -> str
def build_magicmirror(repo_root: Path, enabled: bool) -> None
def render_magicmirror_config(repo_root: Path, env: Mapping[str, str]) -> None
```

Private helpers `_run_npm`, `_is_install_fresh`, `_install_package` keep
`build_magicmirror` short. `_is_install_fresh` returns `True` when
`node_modules/` exists *and* its mtime is ≥ `package-lock.json` mtime —
same freshness pattern as `gcal_setup.py` adapted for npm (MM has no
build step, so there is no `build/index.js` stamp to compare; the lock
file is the canonical "install-invalidator").

`build_magicmirror` loops over four package roots: the MM core plus
three modules. The core install passes `--ignore-scripts`; module
installs do not (their postinstalls are benign). Freshness is checked
per-package — one stale package doesn't force reinstalls on the others.

`render_magicmirror_config` reads `config/config.js.template`, substitutes
the three `${MAGICMIRROR_*}` placeholders (falling back to
`MAGICMIRROR_CONFIG_VARS` defaults when env keys are missing), and
writes the resolved `config/config.js`. The template stays tracked;
the rendered file is gitignored.

### 3. `magicmirror/config/config.js.template`

Hand-authored to spec:

- `address: "${MAGICMIRROR_HOST}"`, `port: ${MAGICMIRROR_PORT}`,
  `ipWhitelist: ${MAGICMIRROR_IP_WHITELIST_JSON}` — three placeholders,
  rendered at setup time.
- No default newsfeed / weather / compliments modules (MM's sample
  ships them; we delete entirely).
- **`MMM-pages` class-based**: `modules: [["page0"], ["page1"],
  ["page2"]]`, `fixed: ["clock", "MMM-WebHookAlerts"]`, `timings:
  { default: 20000 }`. Class-based (not module-name-based) because we
  run three `MMM-Markdown` instances — name-based would only allow one.
- Three `MMM-Markdown` instances, one per page, each with
  `markdownFilename: "tasks.md"` / `"state_buffers.md"` / `"schedule.md"`.
  Files live inside the module dir per the research decision (no
  symlinks). A `classes` CSS tag ties each instance to its page.
- `MMM-WebHookAlerts` in `fullscreen_above` with three templates
  (`state_change`, `buffer_alert`, `missed_checkin`), each rendering
  payload fields (`from_state`, `to_state`, `buffer_name`, etc.) into
  inline-styled dark-theme HTML. No external CSS imports.
- Built-in `clock` in `top_left` (date awareness is useful) — also
  pinned in `MMM-pages.fixed` so it survives page rotation.

### 4. `setup_workspace.py` integration

Two-line additions to imports, three-line additions inside
`setup_workspace()`:

```python
from magicmirror_setup import (
    MAGICMIRROR_WEBHOOK_TEMPLATE_NAMES,
    build_magicmirror,
    is_magicmirror_enabled,
    render_magicmirror_config,
)

# ...inside setup_workspace()...
magicmirror_enabled = is_magicmirror_enabled(env)
build_magicmirror(REPO_ROOT, magicmirror_enabled)
if magicmirror_enabled:
    render_magicmirror_config(REPO_ROOT, env)
```

All four symbols added to `__all__` (identity check in tests requires
it under `mypy --strict`).

### 5. `.env.example` + `.gitignore`

Six new `MAGICMIRROR_*` entries with inline rationale comments — the
flag, host, port, the LAN-widened `ipWhitelist` JSON literal, the
loopback-pinned webhook host, and the webhook port (aliased to MM port
because `MMM-WebHookAlerts` attaches to the MM Express app, not a
separate listener).

Three new gitignore lines: core `node_modules/`, wildcard module
`node_modules/`, and the rendered `config.js` (the `config.js.template`
stays tracked).

## Key decisions

| # | Decision | Reason |
|---|---|---|
| 1 | **`magicmirror_setup.py` as a sibling module to `gcal_setup.py`, not inlined** | Same argument as task 14-01 decision #1: inlining pushes `setup_workspace.py` over the 300-line cap. The magicmirror helpers are a cohesion unit (npm install × 4 packages, template render, feature-flag gate); splitting gives tests one patch point via `patch("magicmirror_setup.subprocess.run", ...)`. |
| 2 | **`--ignore-scripts` on the MM core install only, not on module installs** | The MagicMirror core's `postinstall` runs `git clean -df` — in our vendored tree that would delete `config.js.template` and the `.vendor-source.md` pin. Asserted by `test_core_install_passes_ignore_scripts` and `test_module_installs_do_not_pass_ignore_scripts`. |
| 3 | **Template lives at `config/config.js.template`; rendered `config/config.js` is gitignored** | Mirrors how `workspace/config.json.template` resolves to `~/.nanobot/config.json`: template is human-auditable source, rendered artifact is environment-specific output. Rendering is pure text substitution (no JSON round-trip) so the resulting file stays valid JS — MM parses `config.js` as a Node module, not JSON. |
| 4 | **Freshness check via `node_modules/` mtime vs `package-lock.json` mtime** | MM has no build step (unlike the gcal MCP server with its esbuild pipeline), so there is no `build/index.js` stamp. The lock file is the canonical invalidator — any upstream re-pin or dep bump touches it. Same idempotency story as gcal, adapted for no-build packages. |
| 5 | **Class-based `MMM-pages` config (`[["page0"], ["page1"], ["page2"]]`)** | We run three `MMM-Markdown` instances on three separate pages. Module-name-based pages would collapse all three into one "markdown page." Class-based gives each instance its own CSS tag; `MMM-pages` matches by tag. Research §3.3 confirmed this is the documented pattern. |
| 6 | **`MMM-Markdown` files live inside `magicmirror/modules/MMM-Markdown/markdown/`** | Default location per the module's source. Alternative (symlinks from a stable workspace dir) added complexity sub-02 would have to navigate. Writers in sub-02/sub-03 just drop files into a known in-repo path. |
| 7 | **Webhook host defaults to `127.0.0.1`; MM host defaults to `0.0.0.0`** | Display server must be LAN-reachable for the Fire Tablet. Webhook POSTs originate from the bot process itself, so there's no reason to expose the webhook endpoint to the LAN — `127.0.0.1` pins it. MM's `ipWhitelist` enforces the split at the HTTP layer (LAN-widened for display, loopback-only for webhooks requires the POST source IP to be 127.0.0.1). |
| 8 | **Split the test suite into two files (`test_magicmirror_setup.py` + `test_magicmirror_config_template.py`)** | Single-file version was 443 lines (over 300 cap). Helper behaviours (flag, detect, build, freshness, npm failure) live in `test_magicmirror_setup.py` (240 lines); vendor-integrity + template-content + gitignore + env.example live in `test_magicmirror_config_template.py` (294 lines). |
| 9 | **Omitted `strip_magicmirror_config` reserve-hook from description** | Description §2 mentioned a `strip_magicmirror_config(config) → dict` for symmetry with `strip_gcal_mcp_server`. But MM does not land anything inside `config.json.template` — its config lives in a wholly separate file (`magicmirror/config/config.js.template`). A strip hook with nothing to strip is "just-in-case code" (anti-slop rule #1). If sub-02/sub-03 later add a nanobot config block for MM, it can be added then. |
| 10 | **`MAGICMIRROR_CONFIG_VARS` as a public dict, not three module-level strings** | Gives tests and external callers one canonical place to read defaults (e.g. `test_uses_defaults_when_env_omitted` iterates over it). Same pattern as `ENV_VARS` + `OPTIONAL_ENV_VARS` in `setup_workspace.py`. |

## Deviations from the research plan

Two intentional, both documented above:

1. **`strip_magicmirror_config` helper from description §2 omitted.**
   MM's config lives in `magicmirror/config/config.js.template`, not in
   `workspace/config.json.template`, so there is nothing in the nanobot
   config dict to strip when the flag is off. The flag-off path simply
   skips `render_magicmirror_config` and `build_magicmirror` is a
   no-op. Adding an empty strip hook would be pure "just in case" code
   (anti-slop rule #1). sub-02/sub-03 can add one iff they register an
   MM-related entry inside `workspace/config.json.template`.

2. **Freshness check compares `node_modules/` mtime to
   `package-lock.json` mtime**, not `build/index.js` mtime. MM has no
   build step, so the gcal pattern of "stamp file mtime" maps to the
   lockfile — any upstream dep change touches it. Documented in
   `magicmirror_setup.py`'s `_is_install_fresh` docstring.

## Hand-offs to sub-02 / sub-03

- **Sub-02 (Python webhook client + markdown writers):**
  - Webhook endpoint: `http://${MAGICMIRROR_WEBHOOK_HOST}:${MAGICMIRROR_WEBHOOK_PORT}/webhook?templateName=<name>` — POST with JSON body whose keys match the template's placeholder set.
  - Template names import from `magicmirror_setup.MAGICMIRROR_WEBHOOK_TEMPLATE_NAMES` to stay in sync.
  - Markdown feed paths: write to `magicmirror/modules/MMM-Markdown/markdown/{tasks.md,state_buffers.md,schedule.md}`.
  - Source-IP enforcement: MMM-WebHookAlerts delegates to MM core's `ipWhitelist`. Since the webhook host defaults to `127.0.0.1`, POSTs from non-loopback origins can only succeed if the user widens the whitelist; sub-02's client should always target `127.0.0.1`.
- **Sub-03 (hook-chain wiring + user docs):**
  - `setup_workspace.py` already calls `build_magicmirror` and
    `render_magicmirror_config` — no setup-flow changes needed.
  - The `MAGICMIRROR_ENABLED` flag is the single on/off — sub-03's
    custom-gateway hook should short-circuit on the same flag.
  - `MAGICMIRROR.md` user docs should link to
    `magicmirror/.vendor-source.md` so users can see exact upstream
    provenance.
